# Накладні ФОП і рахунки (LP-CRM)

Сервіс для формування видаткових накладних і рахунків на оплату за замовленнями LP-CRM.

- **Накладні ФОП** — за номером замовлення LP-CRM; ФОП визначається з чека Checkbox, поля 1, відділу або вручну; шаблони, друк, Word, PDF, історія версій.
- **Рахунки (Word)** — з замовлення CRM або вручну; окремий довідник ФОПів рахунків; Word і PDF; кнопка «Надіслати» — файл Word через меню «Поділитися» і текст з посиланням на оплату в Telegram, Viber, WhatsApp або в буфер обміну (також на сторінці посилань на оплату).
- **Аналітика** (власник і адміністратори) — замовлення LP-CRM за 6 місяців: періоди і порівняння, фільтри
  за відділом, джерелом (поле 1), менеджером, брендом і категорією, таргети по обороту на відділи і джерела.
- **B2B партнери** — партнери (компанії) з власними користувачами (роль «Партнер»): власник і адміни вмикають бренди й маржу;
  партнер бачить лише свій кабінет — каталог з РРЦ і своєю ціною (РРЦ − маржа, з ПДВ, до копійок). Каталог — з LP-CRM.
  Юрособи партнера, закупівлі (рахунок і накладна від бухгалтера, файли 30 днів), замовлення для клієнтів партнера
  з залишку закупівлі (ТТН і маркування партнера; «без закупівлі» — червоним). Кнопка «Додати в CRM» (LP-CRM addNewOrder,
  відділ B2B) вмикається в «Замовлення клієнтів» → «Налаштування CRM», коли ключ LP-CRM має дозвіл на addNewOrder;
  до того номер замовлення з CRM вписують вручну — партнер бачить його статус.
  Команда партнера: ролі Керівник / Менеджер / Лише перегляд; керівник сам додає колег (адмін бачить, хто кого додав).
  Видалення партнера: без замовлень — повністю, із замовленнями — в архів (замовлення лишаються).
  Telegram-група партнера (бот + «/link КОД» з картки партнера): детальні закупівлі й замовлення клієнтів, рахунки й накладні файлами, оплата.
  Тестові закупівлі й замовлення клієнтів можна видалити (закупівлю — після її замовлень клієнтів).
  Списки B2B: пошук, період, оплата, галочки й масові дії (оплачено, завершено, скасувати, видалити, «Додати в CRM»).
  Аналітика продажів партнера (у кабінеті партнера й для адміна): продажі, заробіток за РРЦ, закупівлі, борг, залишок, товари, категорії, бренди, дні.
  Каталог партнера: бренди зі знижкою від РРЦ, категорії з кількістю, пошук, сортування, групування за брендами.
  «Надіслати зміни цін» (вручну): нові РРЦ і ціни партнера, зміни знижок — у Telegram-групу партнера або його користувачам.
- **Акаунти** — власник, адміністратори, адміністратори без керування людьми (не додають, не змінюють і не видаляють користувачів і партнерів), менеджери, перегляд, партнери. Доступ до аналітики для кожного вмикає/вимикає власник.

## Локальний запуск

```bash
npm install
npm run build      # збирає dist/: server.mjs + public/ + start.bat
npm start          # http://localhost:8787
```

Для Windows-користувачів: архів папки `dist/` → `start.bat` (потрібен Node.js 22.13+).

## Структура

Код поділено на незалежні блоки: кожен модуль має свої маршрути, свої таблиці й тести,
а до інших модулів звертається лише через їхній публічний вхід (`index.js`). Це перевіряє `tests/architecture.test.mjs`.

```
src/
  app.js           збирає модулі (порядок: auth першим) і передає їм ctx
  migrate.js       міграції: кожен модуль — свої таблиці і своя версія схеми (ключ settings «schema:<модуль>»)
  core/            спільне: база (SQLite / D1), схема, ролі й паролі, налаштування, гроші, дати,
                   лічильник номерів рахунків, перевірка картинок, журнал змін реквізитів
  integrations/    лише клієнти API: lpcrm.js, checkbox.js
  modules/
    auth/          вхід, сесії, користувачі, ролі
    refs/          ФОПи накладних, відділи, «Поле 1», шаблони, загальні налаштування
    nakladni/      пошук замовлення, накладна, версії, історія (віддає loadOrder, normalizeOrder)
    rahunky/       рахунки на оплату (Word), ФОПи рахунків
    admin/         експорт / імпорт налаштувань, журнал змін
    errlog/        журнал помилок (вкладка для адмінів) і сповіщення адмінам у Telegram
    b2b/           B2B: партнери, бренди й маржа, каталог з LP-CRM, кабінет партнера, закупівлі (orders.js), замовлення клієнтів (clients.js)
    payments/      Opendatabot: посилання на оплату, надходження (віддає linkForRahunok)
    notify/        Telegram-сповіщення (віддає notify)
    analytics/     аналітика продажів
public/
  app.js           оболонка: вхід, меню, роутер
  core/ui.js       спільне для сторінок: API, діалоги, повідомлення, друк
  pages/           сторінки: nakladna, refs, rahunky, settings, users (+ an.js, pay.js, anpay.js)
```

Правила: модуль не імпортує внутрішні файли іншого модуля; таблиці модуля пише лише сам модуль;
спільне — тільки в `core/`. Таблиці модуля описані в `modules/<модуль>/schema.js`;
при зміні схеми підвищуйте `version` цього модуля — міграція виконається лише для нього. Чистку за строком зберігання кожен модуль реєструє сам (`onCleanup`).

## Аналітика

- `src/analytics.js` — завантаження замовлень зі статусів «Принят», «Отправлен», «Очікує викупу», «Завершено»,
  «Відмова на пошті», «Повернуто на склад» (кроками, браузер повторює `/api/an/sync/step`), налаштування, таргети,
  запит дашборду `/api/an/query` (підсумки рахує база).
- `public/an.js` — дашборд і налаштування аналітики.
- Сума замовлення — фактична з CRM (зі знижкою); на товари розподіляється пропорційно.
- Відділ: спершу за менеджером, потім за відділом CRM (перемикається в налаштуваннях). Джерело — за «Поле 1»,
  далі «сайт», utm_source. Бренд — за ключовими словами в назві товару.
- Таргет — на місяць, на відділ або джерело (відділ без свого таргету = сума джерел); на період — пропорційно дням.
- Розраховано на ліміти безкоштовного Cloudflare: ≤ 50 запитів до D1 на звернення, мало індексів (записів у базу
  на добу ≤ 100 тис.), JOIN з фіксованим порядком таблиць.

## Тести

```bash
node --no-warnings tests/flow.test.mjs
node --no-warnings tests/auth-rahunky.test.mjs
node --no-warnings tests/real-shape.test.mjs
node --no-warnings tests/ratelimit.test.mjs
node --no-warnings tests/analytics.test.mjs
node --no-warnings tests/d1-budget.test.mjs   # кількість запитів до бази на одне звернення
node --no-warnings tests/security.test.mjs    # картинки ФОП (XSS) і номери рахунків без дублів
node --no-warnings tests/architecture.test.mjs # модулі залежать один від одного лише через index.js
node --no-warnings tests/ui-smoke.test.mjs     # інтерфейс: усі сторінки відкриваються без помилок JS
node --no-warnings tests/migrate.test.mjs      # міграції модулів не змінюють наявних даних
```

GitHub Actions (`.github/workflows/ci.yml`) запускає всі тести на кожен push і pull request.
У pull request він сам збирає `functions/api/[[path]].js` і комітить його в гілку; у `main` — перевіряє,
що файл зібрано з поточного `src/`.

Заголовки безпеки сторінок (Content-Security-Policy та інші) — у `public/_headers` (Cloudflare Pages)
і в `src/server-node.js` (локальна версія).

Ключі API, база даних і папка `data/` у репозиторій не потрапляють.

## Cloudflare Pages

Сайт: **https://ecovent-nakladni.pages.dev** (Pages, гілка `main`, автоматичне розміщення з GitHub).

- Статичні файли — папка `public/` (Build output directory = `public`, Build command — порожньо).
- Серверна частина — `functions/api/[[path]].js` (готовий файл, збирається командою `npm run build` з `src/pages-entry.js`).
  **Після змін у `src/` обов'язково виконайте `npm run build` і закомітьте оновлений файл.**
- База — Cloudflare D1, binding з іменем **`DB`** (Settings → Bindings). Таблиці створюються автоматично.
- Ліміти безкоштовного плану враховано: ≤40 зовнішніх запитів на звернення (довгий пошук у LP-CRM
  продовжується автоматично наступними зверненнями), легший хеш пароля (10 000 ітерацій PBKDF2).

Необов'язкові змінні середовища (Settings → Variables and Secrets):

| Змінна | Призначення |
|---|---|
| `OWNER_RESET_PASSWORD` | Новий пароль власника (від 6 символів). Застосовується один раз; після входу змінну краще видалити. |
| `PBKDF2_ITERATIONS` | Кількість ітерацій хешу пароля (за замовчуванням 10000). |
| `MAX_SUBREQUESTS` | Ліміт зовнішніх запитів на звернення (за замовчуванням 40). |

Перенесення налаштувань з локальної версії: **Налаштування → Перенесення налаштувань** (експорт у файл → імпорт на сайті).

Локальна перевірка в середовищі Cloudflare: `npm run build && npm run dev:cf`.
